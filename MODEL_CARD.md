#### Description

`facebook/esm2_t30_150M_UR50D` is the 150M-parameter member of the ESM-2 protein language model family (Lin et al., bioRxiv 2022.07.20.500902), pinned here to revision `a695f6045e2e32885fa60af20c13cb35398ce30c`. ESM-2 is a bidirectional transformer encoder trained by masked-token prediction on UniRef protein sequences; the pinned `config.json` names 30 hidden layers, hidden size 640, 20 attention heads, intermediate size 2560, rotary position embeddings, a 33-token vocabulary and `max_position_embeddings` 1026, and the Hub reports 148.8M parameters. At inference the model reads one amino-acid residue per token and returns a contextual 640-dimensional hidden state per residue; it produces a representation, not a task prediction, and it is adapted by gradient training rather than by in-context conditioning. What this repository adds is the `ESM2Pipeline` class in `src/esm2_protein_pipeline/pipeline.py`: manifest verification of the 6-file snapshot before any model library is imported (`verify_snapshot`), fresh-clone staging at the pinned revision only (`stage_missing_files`), a loader that reads the local verified directory with `local_files_only=True` and `trust_remote_code=False`, input validation against a named amino-acid alphabet and explicit ceilings (`validate_inputs`), mean-pooled sequence embeddings over residue tokens (`embed`), bounded gradient fine-tuning of an `EsmForSequenceClassification` head plus the last *n* encoder layers (`adapt`), held-out classification metrics (`evaluate`), argmax classification with per-class scores (`classify`), and a safetensors adapter artifact with a digest manifest that is verified before deserialization and reloads against the pinned base (`save_artifact`, `from_artifact`). The dataset contract, the deterministic tutorial sample and the trivial baselines live in `samples.py` and `metrics.py`.

#### Intended Use and Limitations

###### Primary Intended Uses

Two tasks are exposed. **Sequence representation:** input is 1 to `MAX_SEQUENCES_PER_CALL = 64` protein sequences of 1 to `MAX_RESIDUES = 1022` residues as uppercase one-letter strings; output is one 640-dimensional vector per sequence (the mean of the last hidden state over residue tokens, `<cls>`/`<eos>`/padding excluded), suitable as features for a downstream model, for similarity search over a protein set, or for clustering. **Sequence classification:** given a labelled dataset of `{id, sequence, label}` records with 2 to 20 classes, the pipeline fine-tunes a classification head (optionally with the last encoder layers) and then predicts a class with per-class scores for new sequences. Envisioned application domains are protein-engineering and bioinformatics workflows where a modest labelled set exists — family or subtype assignment, predicting a binary functional property measured in an assay, triaging candidate sequences before wet-lab work, and teaching or evaluating protein-LM transfer learning. In a larger system the pipeline is a feature extractor and a fine-tuning baseline whose output feeds human review or a downstream model, not an autonomous annotation service.

###### Primary Intended Users

Intended users are machine-learning engineers, computational biologists and bioinformaticians building or evaluating protein-sequence models, in research, internal enterprise, or the DIMER model workbench. The pipeline assumes its users understand that a pretrained protein language model encodes sequence statistics rather than validated biology; that a random split of homologous sequences leaks information and inflates every metric, so homology-aware splitting is their responsibility (the pipeline does not detect homology); that the softmax scores it returns are uncalibrated; that sequences beyond 1,022 residues are refused rather than truncated and must be split or the request rethought by the caller; and that a fine-tuned classifier is only as good as the labels supplied, which the pipeline cannot audit.

###### Out-of-scope use cases

1. **Capability boundary:** the pipeline exposes whole-sequence embeddings and whole-sequence classification only. It does not perform residue-level (token) classification, contact-map or structure prediction, masked-token scoring or sequence generation/design, variant-effect scoring, multiple-sequence alignment, or regression on a continuous target; `EsmForMaskedLM`, ESMFold and the larger ESM-2 checkpoints are separate packages and are not loaded here.
2. **Input boundary:** sequences must be uppercase one-letter strings over `ACDEFGHIKLMNPQRSTVWY` plus the ambiguity codes `BUZOX`; lowercase letters, alignment gaps (`-`, `.`), whitespace, digits and nucleotide-only input are rejected with a `ValueError` naming the offending characters, never silently mapped to `<unk>`. At most 64 sequences per call and 1,022 residues per sequence (`MAX_RESIDUES`, the 1,024-token training window minus `<cls>` and `<eos>`); a dataset needs at least 12 records, at least 3 per class, at most 5,000 records and at most 20 classes, with unique ids and unique sequences. Nucleotide sequences, protein structures, and images are not inputs.
3. **Decision boundary:** not for autonomous action on a predicted class — clinical or diagnostic interpretation, patient or therapeutic decisions, biosafety or pathogenicity screening, regulatory submission, or any decision taken without a domain expert reviewing the evidence and without task-specific validation on data from the deployment's own distribution. A score above any threshold is not evidence of a biological property.

#### Factors

###### Groups

The pipeline is not human-centric in the demographic sense: its inputs are protein sequences, not people or data about people, so age, gender, skin type and socioeconomic status are not attributes of any input and no demographic evaluation applies. The factors its behaviour does vary with are biological and technical: the taxonomic origin of a sequence, its protein family and how densely that family is represented in UniRef, sequence length, the fraction of ambiguity codes, and — for the classifier — class balance and the homology structure between training and evaluation sequences. Neither the upstream authors nor this repository audits the UniRef pretraining corpus for taxonomic or family imbalance, and no such audit was performed here; well-studied model organisms and large families are over-represented in public sequence databases, so representation quality is uneven in a way this pipeline cannot measure. The downstream operator must therefore stratify their own evaluation by the factors that matter to them — at minimum by taxon or family and by sequence length — and check that per-group accuracy does not hide behind an aggregate number. Where a deployment links proteins to individual people (human variant data, patient-derived sequences), the operator inherits the full set of personal-data obligations; the pipeline neither detects nor supports that case.

###### Instrumentation

There is no sensor in the usual sense. The pretraining data is UniRef, a clustered redundancy-reduced view of UniProt: sequences determined by DNA sequencing and translation, by mass-spectrometry-based proteomics, or by direct protein sequencing, then assembled and curated by database pipelines. The instrument characteristics that matter are therefore database characteristics: gene-model and translation errors propagate into "protein" sequences that were never observed as proteins; UniRef clustering at a fixed identity threshold removes near-duplicates unevenly across families; curation status varies between reviewed (Swiss-Prot) and unreviewed (TrEMBL) entries; and sequencing depth and choice of organism are set by research funding, not by biological importance. At inference the pipeline passes the caller's sequence verbatim: no gap removal, case normalisation, ambiguity-code substitution, trimming of signal peptides or tags, or de-duplication. Defects in the operator's own pipeline — a mis-translated ORF, a retained expression tag, a sequence read from the wrong frame, a truncated entry — reach the model unchanged, and the pipeline detects only the shape errors it validates (alphabet, emptiness, length ceilings, duplicate ids and sequences, class coverage). Labels are a second instrument: whatever assay, annotation transfer, or database field produced the training labels carries its own error rate into the fine-tuned head, and the pipeline has no way to see it.

###### Environment

Operating environment: Python 3.12 with `torch==2.14.0` (the venv build is `2.14.0+cu130`), `torchvision==0.29.0`, `torchaudio==2.11.0`, `transformers==4.57.6`, `huggingface-hub==0.36.2`, `safetensors==0.8.0`, `numpy==2.5.3` (`pyproject.toml`); the loader maps weights to CPU and moves the model to `device`, which defaults to `cuda:0` when CUDA is visible and `cpu` otherwise. Only float32 is exercised — no quantisation, autocast, or compiled kernels — and the executed CPU run is recorded under "Runtime" (verify + load 7.2 s; 4-epoch adaptation on 56 sequences 36.1 s; the whole workflow 46.9 s on the reference machine). Memory scales with batch size times the longest sequence in the batch, because the batch is padded to that length; a 64-sequence batch of 1,022-residue sequences is the worst case the ceilings allow and was not measured. Data environment: the model assumes natural protein sequences resembling UniRef. Its representations degrade, without any error, on de novo designed or randomised sequences, on heavily engineered constructs with long non-natural linkers or tags, on fragments shorter than a domain, and on families absent from the pretraining corpus. For the classifier the load-bearing assumption is that evaluation sequences are drawn from the same distribution as the training ones *and are not homologous to them*: if related sequences straddle the split, the reported metrics measure memorisation of a family rather than generalisation, and the pipeline cannot detect this for the operator.

#### Metrics

###### Performance Measures

The pipeline reports, exactly as `metrics.classification_metrics` names them: `accuracy` (share of sequences whose argmax class is correct), `macro_f1` (unweighted mean of per-class F1 over classes present in the split), `per_class` precision/recall/F1 with `support` and `predicted` counts, and `auroc` (area under the ROC curve; for two classes the positive class is the last entry of the class list, for more it is the macro one-vs-rest average, computed from the Mann-Whitney rank statistic with average ranks for ties). Accuracy alone is misleading on an imbalanced set — a classifier that always answers the majority class can score well — which is why macro-F1 and the per-class rows are returned with it; and both are threshold-dependent, which is why AUROC is returned too: it measures whether the model *ranks* the positive class above the negative one independently of the argmax rule, so an under-trained head can show high AUROC with near-chance accuracy. Two baselines are reported with the same fields for comparison: `majority_baseline` (predict the most frequent training class) and, for binary tasks, `composition_baseline` (one threshold on the hydrophobic residue fraction fitted on the training split only). The embedding stage reports **no** performance measure: it emits a 640-dimensional representation with no label, and the caller must supply a labelled downstream task, or a reference set with known relationships, before any quality claim about the embeddings can be made. The executed CPU run recorded under "Runtime" is sample-sanity evidence on a synthetic 20-record test split, not a benchmark; no upstream benchmark number is reproduced in this repository.

###### Decision thresholds

The default decision rule for `classify` is an `argmax` over `softmax(logits)` — an implicit threshold, and the only one the pipeline applies. No tuned operating point ships: the pipeline deliberately emits the full per-class score dictionary alongside the argmax label so that a deployment can apply its own rule, and calibrating that rule is the operator's job. Choose it from the asymmetric cost in your setting: for triage before expensive wet-lab validation a false positive costs an experiment while a false negative discards a candidate silently, so a low threshold on the positive class with human review of the borderline band is usually right; for a classifier whose output populates a database field, a high threshold plus an explicit "unassigned" outcome is safer than forcing every sequence into a class. The thresholds that *were* set during development are input-contract limits, not decision thresholds: `MAX_RESIDUES = 1022` (the 1,024-token training window minus the two special tokens — beyond it the model degrades silently, so the pipeline refuses), `MAX_SEQUENCES_PER_CALL = 64`, at least 12 dataset records and 3 per class (below which a held-out split cannot carry any class), at most 5,000 records and 20 classes. No accuracy acceptance threshold was set, because this repository ships no task for which one would be meaningful.

###### Approaches to uncertainty and variability

Reported metrics come from a **single seeded holdout**: `split_dataset` stratifies by class with an explicit seed (default 42) into train/validation/test, and `evaluate` scores one split once. No cross-validation, bootstrap or repeated-run averaging is performed, and no standard deviation or confidence interval is reported — with the 20-record tutorial test split, any dispersion estimate would be dominated by the split itself. A caller who needs one repeats the workflow over several seeds, or supplies enough labelled data for k-fold, and owns that design. Sources of run-to-run variability inside the pipeline: the split (seeded), shuffling of training batches (seeded through `random.seed`), classification-head initialisation and dropout (seeded through `torch.manual_seed`/`torch.cuda.manual_seed_all`), and non-deterministic GPU kernel selection and float accumulation order, which are **not** controlled by a seed and can move scores in their low-order digits — enough to flip a sequence whose two class scores are close. The forward pass itself runs under `torch.no_grad()` in `eval()` mode, so inference on a fixed device and dtype is otherwise deterministic. The per-class scores are softmax outputs of a head trained on a small labelled set; they are **not calibrated probabilities**, and a caller who needs calibrated confidence must fit a calibrator (Platt scaling, isotonic regression) on held-out labelled data of their own. Embeddings carry no uncertainty estimate of any kind.

#### Ethical considerations and biases

###### Data

Upstream discloses the pretraining data as UniRef protein sequences — the checkpoint name records UniRef50 clustering, and the paper describes training on UniRef sequences with UniRef50-based sampling — and discloses no further breakdown of taxonomy, curation status or per-family composition; that is where upstream disclosure ends, and this repository adds none. Protein sequences are not personal data in themselves, but the corpus is not free of sensitivity concerns: it includes human protein sequences, sequences from pathogens, and entries derived from clinical and patient-derived material, and whether any individual entry is traceable to a person is not established either way by the upstream authors — it is unknown, not ruled out. This repository distributes code, tests and documentation; it does **not** vendor the weights in Git (`weights/esm2-t30-150m-ur50d/model.safetensors` is git-ignored and reproduced from the pinned revision by `stage_missing_files`), and it ships no protein dataset — the tutorial data is generated in code from a seeded random process and contains no natural sequence. The operator owns the audit of whatever they submit: human or patient-derived sequences may be personal or health data under their jurisdiction's law, unpublished sequences may be confidential or third-party proprietary, and sequences of regulated agents may be export-controlled. The pipeline performs none of these checks and transmits nothing — inference is local — but it also does not stop anything.

###### Human Life

This pipeline is not intended for decisions in health, safety, criminal justice, employment, credit, or housing, and it has not been validated or certified for any of them by anyone. No clinical validation, no regulatory clearance, no external review board and no testing with any specific group has taken place; the only evidence in this repository is the offline unit suite (36 tests) and one executed CPU run on synthetic data recorded under "Runtime". Use in a sensitive domain is nevertheless foreseeable — protein models are applied to variant interpretation, antimicrobial-resistance prediction, vaccine and therapeutic candidate triage — and would be admissible only with a domain expert reviewing every consequential output, independent validation on data representative of the deployment with homology-aware splits, evidence that the labels themselves are fit for the purpose, and whatever clinical-laboratory, regulatory and biosafety clearance the domain and jurisdiction require. A predicted class from this pipeline is a hypothesis to test, never a result to act on.

###### Mitigations

1. **Supply-chain integrity:** `MODEL_ID` and the 40-hex `MODEL_REVISION` are module constants; `verify_snapshot()` checks `modelId`, `revision`, and the byte size and SHA-256 of all 6 manifest entries before any load and raises on the first mismatch (tests flip one digit, change the revision and delete a file and assert each raises; the executed run verified all 6 entries including the 595,257,706-byte weight file). `stage_missing_files()` fetches only manifest-listed files absent on disk, only at `MODEL_REVISION`, only when `allow_download=True`, and refuses a manifest naming another model. The loader reads the verified directory with `local_files_only=True`, `trust_remote_code=False` and `use_safetensors=True`, so no remote code executes and the legacy `pytorch_model.bin` pickle is never loaded; `.gitattributes` carries `weights/** -text` so a Windows checkout cannot corrupt a digest through line-ending conversion.
2. **Artifact integrity:** the exported adapter is safetensors, not a pickle, and `load_artifact` checks the artifact format string, the recorded base model id *and revision*, the class list, and the size and SHA-256 of every listed file **before** deserialising, then refuses any tensor name the base architecture does not have (five tests drive these refusals).
3. **Input integrity:** `embed`, `classify` and `validate_inputs` route through one checker, so their acceptance criteria cannot diverge; it rejects non-string input, empty sequences, sequences past the residue ceiling, characters outside the declared alphabet (naming them), too many sequences, and id lists that are the wrong length or not unique. `validate_dataset` additionally rejects missing columns, duplicate ids, duplicate sequences, fewer than 2 or more than 20 classes, and any class with fewer than 3 records, and returns a manifest recording the observed ceilings and a SHA-256 digest of the rows.
4. **Import boundary:** verification and validation run before `torch`, `transformers` or `safetensors` are imported (fleet RTM-001); `tests/test_import_boundary.py` fails if a rejected request reaches a model library.
5. **Statistical mitigations:** `split_dataset` stratifies by class so every split keeps the class proportions, preprocessing state is not fitted at all (the tokenizer is fixed and pinned, so there is nothing to leak), validation metrics are used for monitoring only and the final epoch is kept rather than the best, and two trivial baselines are computed on the same split so a reported number always has a floor to be read against.
6. **Reproducibility:** every runtime dependency is pinned with `==`; splits, shuffling and initialisation take explicit seeds; every result carries `model_id` and `model_revision`; the adaptation record carries the full hyperparameter set and the trainable-parameter names and counts; `load_warnings` preserves whatever the libraries warned at load.
7. **Refusals:** masked-token scoring, residue-level outputs, structure prediction, regression targets, sequences past the training window, and remote code are deliberately not exposed; full-parameter fine-tuning is bounded by the `trainable_layers` parameter (0..30) rather than being the default.

###### Risks and harms

1. **Homology leakage inflating every metric:** the pipeline's random stratified split assumes independent records. Related sequences on both sides of the split turn memorisation into apparent generalisation; the operator bears the harm as a model that fails on genuinely novel sequences after passing its own evaluation. Likelihood is high on real protein datasets assembled from a database query, and the pipeline gives no warning — `split_dataset` documents the assumption, it cannot check it.
2. **Overconfidence outside the pretraining distribution:** on designed, randomised or heavily engineered sequences the encoder still returns a fluent-looking representation and the head still returns a confident-looking score; nothing in the output signals that the input is out of distribution. Harm falls on whoever acts on the prediction — wasted experiments at best, a mistaken biological conclusion at worst.
3. **Label error propagating silently:** the fine-tuned head learns whatever the supplied labels encode, including annotation transferred by homology from a single mis-annotated entry. The resulting model reproduces that error at scale and the metrics, computed against the same labels, look fine.
4. **Uncalibrated scores read as probabilities:** a softmax score of 0.86 from a head trained on a few dozen sequences is a ranking, not an 86 % chance. A downstream system that thresholds it as a probability will mis-state its own error rate; the card and the notebook say so, but the number is easy to misread.
5. **Automation bias in triage:** used to rank candidates for experimental work, the model shapes what gets tested and therefore what future labels exist — a feedback loop that can entrench a family or taxon bias inherited from the pretraining corpus. The harm is diffuse and slow, borne by the research programme rather than by any single decision.
6. **Sensitive input handled without an audit:** the pipeline will happily embed human, patient-derived or export-controlled sequences; it performs no check and the operator may not realise one was needed. Inference is local and transmits nothing, which bounds the exposure but does not discharge the obligation.

###### Use cases

The pipeline must not be used to design, optimise, screen or triage sequences for toxins, pathogens, or any agent intended to cause harm, nor to circumvent biosecurity screening of synthesised sequences. It must not be used to infer, from a person's protein or variant sequences, health status, disease risk, ancestry or any other personal characteristic used to make decisions about them — in employment, insurance, credit, education, immigration or healthcare access — or to build profiles of identifiable individuals from genomic or proteomic material. It must not be used to produce clinical or diagnostic outputs presented to patients or clinicians as validated, nor to generate annotations deposited into public sequence databases without marking them as model-predicted, which would pollute the corpora that future models train on. It must not be used to process sequences the operator has no right to process — confidential, third-party proprietary, or export-controlled material — or in any way that breaches the MIT terms of the upstream weights or the DIMER deployment terms. These prohibitions hold even where the model would produce an accurate answer.

## Input/output contract

- `ESM2Pipeline.from_pretrained(device=None, weights_dir=None, allow_download=False)`: stages and verifies the snapshot, then loads `EsmModel` (no pooling layer) and the `EsmTokenizer` from the verified directory with `local_files_only=True`, `trust_remote_code=False`, `use_safetensors=True`; `device` defaults to `cuda:0` when visible, else `cpu`. `load_warnings` holds any warnings emitted at load.
- `embed(sequences, *, names=None) -> dict` with keys `ids`, `embeddings` (one 640-float vector per sequence), `dimension`, `pooling`, `unit`, `n_sequences`, `model_id`, `model_revision`.
- `adapt(train_records, val_records=None, *, classes=None, epochs=4, learning_rate=1e-4, batch_size=8, trainable_layers=2, weight_decay=0.01, seed=42) -> dict`: bounded AdamW fine-tuning; returns the method description, class list, hyperparameters, trainable/total parameter counts, trainable parameter names, split sizes, the selection rule and the per-epoch history.
- `evaluate(records) -> dict`: `n`, `accuracy`, `macro_f1`, `per_class`, `classes`, `decision_rule`, `auroc`, `auroc_definition`.
- `classify(sequences, *, names=None) -> dict` with `predictions` (each `{id, residues, label, score, scores}`), `classes`, `decision_rule`, `n_sequences`, `model_id`, `model_revision`, `adaptation`.
- `save_artifact(output_dir, metadata=None) -> Path` writes `adapter.safetensors` + `manifest.json` (format, base model id/revision/licence, class order, file sizes and SHA-256, tensor names, adaptation record); `from_artifact(artifact_dir, ...)` / `load_artifact(...)` verify all of that before deserialising.
- `validate_inputs(sequences, *, names=None)` and `validate_dataset(records, *, classes=None, ...)` return the input and dataset manifests; both raise exactly what the execution path would raise.
- Constants: `MAX_RESIDUES = 1022`, `MAX_SEQUENCES_PER_CALL = 64`, `HIDDEN_SIZE = 640`, `STANDARD_AMINO_ACIDS = "ACDEFGHIKLMNPQRSTVWY"`, `EXTENDED_AMINO_ACIDS = "BUZOX"`, `MIN_RECORDS = 12`, `MIN_RECORDS_PER_CLASS = 3`, `MAX_RECORDS = 5000`, `MAX_CLASSES = 20`, `ARTIFACT_FORMAT = "org.valcorza.esm2-protein.adapter.v1"`.
